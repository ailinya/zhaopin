## 3. 推荐阅读顺序（按角色）

### 3.1 新人 onboarding（第 1 天）

```
00_requirements（先知道做什么 + 为什么）
   ↓
01_architecture（架构概览）
   ↓
07_deployment（按手册跑通 dev 环境）
   ↓
04_implementation（看历史/现状 + 已落地状态）
                        ↓
        后端方向看 02 + 03 + 05 + 06
        前端方向看 02 + 06 + 08
```

**预计时间**：
- 纯阅读：2-3 小时
- 含跑通本地环境：半天

### 3.2 后端开发

```
01_architecture（架构概览）
  ↓
02_backend_api_spec（API 契约）
03_data_model（数据模型）     ← 跟 02 平行读
  ↓
05_langgraph_workflow（核心业务流）
06_sse_events（事件契约）
  ↓
04_implementation（实施现状 + 未解决限制）
  ↓
07_deployment（部署流程）
```

**日常参考**：02 / 03 / 05 / 06 翻得最多，建议 IDE 装 Markdown 预览插件。

### 3.3 前端开发

```
01_architecture（架构概览）
  ↓
02_backend_api_spec（要知道后端给什么）
06_sse_events（SSE 消费）
  ↓
08_frontend_design_spec（页面/组件/状态/鉴权全在这里）
  ↓
04_implementation（看现状）
```

### 3.4 部署 / 运维

```
07_deployment（开发 + 部署全流程：环境依赖 + dev 启动 + Docker Compose + Nginx + 备份/升级 + IDE 工具链）
  ↓
04_implementation（已知限制 → 监控重点）
```

> **07 是唯一的部署手册**：开发机环境（apt / Windows GTK / .env）+ 本地 dev 启动 + 生产 Docker Compose 部署全在一个文档里，运维角色只看 07 即可。

### 3.5 架构师 / Tech Lead

```
../重构架构讨论.md（设计决策全貌）
  ↓
01_architecture（实现对照）
  ↓
04_implementation（哪些偏离了原设计 + 为什么）
  ↓
05 / 06 / 08（子系统深入）
```

## 6. 文档维护规则

### 6.1 编号约定

- `00` ~ `08`：核心规范，按阅读顺序
- 不进编号的：辅助资料（教程 / 笔记 / 工具指南）
- 新增核心规范 → 按现有最大编号 + 1（不要插队）

### 6.2 更新时机

| 触发条件 | 更新 |
|---|---|
| 后端代码改动 API / 模型 / LangGraph | 02 + 03 + 05 |
| 后端代码改动 SSE 推送 | 06 |
| 前端代码改动页面 / 组件 / Hook | 08 |
| 增减依赖 / 改部署流程 / 系统依赖 / .env / IDE 配置 | 07 |
| 新增 / 变更功能模块 / 用户角色 / 业务流程 / 验收标准 | 00 |
| 完成一个 Week 实施 | 04 |
| 架构级决策变更 | 01 + `../重构架构讨论.md` |

### 6.3 版本号

- `-v1.0.md`：稳定版
- `-v2.0.md`：重大重写
- 大版本号变更时，README 表格里同步更新

### 6.4 一致性校验

每次 PR 应检查：
- 文档之间的引用路径还正确吗（`../重构架构讨论.md` 而不是 `D:\...`）？
- 数量级数字（表数、API 数、测试数）一致吗？
- 状态标记（✅ / ⏳ / 远期）一致吗？

## 7. 文档贡献流程

新增 / 修改文档时：

1. **小改**（typo / 表格更新）：直接 PR，标题 `[docs] <文件名>:<简述>`
2. **新增章节**（在已有文档里加节）：同上
3. **新增文件**（新文档）：
   - 在本文档 §2.1 / §2.2 添加对应行
   - 在 §4 关系矩阵更新
   - 在 §6.4 一致性校验项里加新检查点
